# 0027. In-house text shaping and font fallback

- Status: Accepted
- Date: 2026-11-24

## Context

ADR 0021 step 4 replaces cosmic-text. ADR 0025 added segmentation and ADR 0026 font parsing and rasterization. This part turns text into positioned glyphs: shaping, plus the font fallback that picks a font for each part of a message.

Chat text in Duydaş's three languages needs:

- Turkish: precomposed and decomposed letters (ş, İ, ğ), `locl` forms for dotted and dotless i in ligatures, kerning and mark positioning;
- Japanese: kana and kanji from a Japanese font, with the Latin and Turkish letters that font may lack (Noto Sans JP has no ş or ı, ADR 0026) taken from another font;
- English: ligatures, kerning, and the features a user may turn on (old-style figures, fractions, stylistic sets).

HarfBuzz is the reference: browsers, Qt and cosmic-text (through rustybuzz) shape with it, so text that matches its output looks the way users expect.

## Decision

- **`duydas_text::shaping`, with no dependencies and no `unsafe`.**
  - `shape(font, text, options)` returns glyphs in visual order with advances and offsets in font units, and each glyph's cluster as a byte offset into the text.
  - `itemize(text, fonts)` splits text into runs of one script and one font.
  - `ShapeOptions` carries the `Script`, the `Language` (from a BCP 47 tag such as `tr-TR` or `zh-Hant-TW`, mapped to its OpenType language system as HarfBuzz maps it, with HarfBuzz's fallback from `ZHTM` to `ZHH ` for Chinese in Macao) and `Feature` settings.
  - `duydas_text::font` gains the GDEF, GSUB, GPOS and `kern` readers in a private `layout` module.
- **Output identical to HarfBuzz 10.4.0** for horizontal left-to-right text in scripts that need no script-specific shaper: glyphs, advances, offsets, and clusters up to the cluster model below. Where the specification leaves room, HarfBuzz's choice is taken.
- **Font fallback.** Each grapheme cluster gets the first font in the list that covers all its characters. A character also counts as covered when the font has its canonical decomposition, a space the font lacks when the font has U+0020, a character with a variation selector when the font has that sequence, and a letter with marks when shaping composes them into a glyph the font has (e and U+0301 into é). Default ignorables need no glyph. Common and Inherited clusters (spaces, digits, punctuation) stay with the font before them when it covers them. A cluster no font covers goes to the first font that has its first character, or else stays with the font before it, and shows the missing-glyph box for what that font lacks. The order of the list is the caller's policy: for Japanese text, a Japanese font before a Chinese one.
- **Scripts.** Common and Inherited characters take the script before them, or after them at the start of the text. The Script property comes from Unicode 18.0, generated by `cargo xtask unicode-gen` along with canonical decompositions, compositions, combining classes, general categories and default ignorables (`shaping_tables.rs`).
- **Characters to glyphs**, as HarfBuzz normalizes:
  - a character the font lacks is decomposed when the font has its parts;
  - a base and the marks after it that include a variation selector map as a variation sequence, or nominally;
  - up to 32 marks in a row are put in canonical order;
  - a base and a mark the font has a precomposed glyph for are composed again;
  - a space the font lacks is drawn with U+0020 at the width it should have (em fractions, figure and punctuation widths);
  - Hangul is handled as HarfBuzz's Hangul shaper does: jamo compose into a syllable the font has, a syllable the font lacks is decomposed, and the jamo left get `ljmo`, `vjmo` and `tjmo`.
- **Feature planning**, as HarfBuzz's map builder compiles features:
  - the default features in HarfBuzz's order (`rvrn` in a GSUB stage of its own; `ltra`, `ltrm`; `frac`, `numr`, `dnom` for automatic fractions around U+2044; `rand`; the common and horizontal features), then the caller's, the last setting of a tag winning;
  - requests merged per tag, each feature found in the script and language system given mask bits (the global bit for global features with value 1, otherwise up to 8 bits from bit 4, until the 32 bits run out), lookups sorted by index with their features' masks combined;
  - per glyph masks for automatic fractions and the Hangul jamo features;
  - alternate substitution picks by the glyph's mask bits, so features sharing a lookup combine their values as HarfBuzz's do, and `rand` draws from HarfBuzz's generator, which gives the same sequence;
  - FeatureVariations at the default instance (`rvrn` and the like), and required features in their stage.
  - Plans are cached per font, 16 at a time.
- **GSUB**: all lookup types, contexts and chained contexts in all formats, extension lookups, reverse chaining. Lookup flags, mark attachment classes and mark filtering sets apply; default ignorables are passed over when they do not match, ZWJ and ZWNJ by the feature's rules. Glyphs keep HarfBuzz's ligature properties (ligature id, component), so marks know which component of a ligature they follow, also when a ligature takes in another one.
- **GPOS**: single, pair (both formats), cursive, mark-to-base, mark-to-ligature, mark-to-mark, contexts and extensions. Attachments are resolved into offsets afterwards.
- **Without GPOS kerning**, the legacy `kern` table (formats 0 and 2, Microsoft and Apple headers, cross-stream subtables). **Without GPOS**, marks are placed by combining class from the glyphs' boxes, as HarfBuzz's fallback positioning does: for TrueType the box each glyph's header records, for CFF the outline's.
- **Default ignorables** (joiners, variation selectors, CGJ) take part in matching and are then drawn as zero-width spaces, or dropped when the font has no space glyph. As in HarfBuzz, a COMBINING GRAPHEME JOINER stops substitutions from reaching over it while it keeps marks out of canonical order, decided before marks compose again.
- **Clusters are grapheme clusters.** A glyph's cluster is the start of a UAX #29 grapheme cluster (ADR 0025), never inside one, and clusters do not decrease from one glyph to the next. HarfBuzz's clusters are finer in places (at ZWNJ and between Hangul jamo); a caret never needs to stop there.
- **Hostile fonts cannot make shaping run away.** Every read is bounds-checked, with offsets that stay inside their table, so 32-bit targets cannot overflow either. The work is bounded as HarfBuzz bounds it:
  - a budget of steps per run, 4,096 per character and at least 2²⁰, which every glyph visited, subtable and rule tried, glyph passed over while matching, glyph moved by an edit, cluster merged, mark renumbered, and each glyph a `kern` subtable or fallback positioning goes over spends; when it runs out the remaining lookups do nothing;
  - a buffer at most 32 times the text, and at least 2¹⁴ glyphs;
  - contexts and ligatures matching at most 64 glyphs, nested at most 64 deep;
  - per font, 2²² coverage entries read for lookup digests (HarfBuzz's set digests, which let a lookup pass over glyphs it cannot apply to) and 2¹⁶ digests kept; per plan, 2²⁰ records read for lookup selection.
- **Not supported yet:**
  - scripts that need a script-specific shaper: Arabic, Syriac and the other joining scripts, the Indic scripts, Thai, Lao, Khmer, Myanmar, Tibetan and the Universal Shaping Engine's;
  - right-to-left and vertical text, and bidirectional reordering;
  - AAT (`morx`, `kerx`, `trak`) and `kern` formats 1 and 3;
  - device tables and font variations (positions are those of the default instance);
  - HarfBuzz's modified combining classes for Hebrew, Arabic, Thai and others;
  - HarfBuzz's cluster levels other than the grapheme model above.

  Text in these scripts still shapes, with the default features, and is not compared with HarfBuzz.

## Verification

- **HarfBuzz 10.4.0 on installed fonts.** An ignored test writes this engine's output for 437 faces (the system fonts of the development machine, Acrobat's CFF fonts and the DejaVu fonts), 70 texts and 9 feature and language settings, and a script shapes the same with HarfBuzz through its C API. All **275,310 runs match** in glyphs, advances and offsets.
  - The texts cover Turkish, Japanese, English, Greek, Cyrillic, Armenian, Georgian, modern and Old Hangul, emoji with ZWJ sequences, decomposed and stacked marks, fractions, ligature and kerning pairs, spaces of every width, joiners and variation selectors, and random strings.
  - Clusters are compared strictly: HarfBuzz's are floored to grapheme starts and ours must equal them. One difference is allowed: a mark after a control or format character starts a grapheme in UAX #29, where HarfBuzz keeps it in the cluster before.
- **Synthetic fonts.** 199 cases reach what installed fonts do not, on fonts built with fontTools, the unit tests' fonts, and DejaVu Sans with its GPOS removed: shared and random alternates, mask bits running out, Hangul with `calt`, `kern` tables with cross-stream subtables, fractions with multiple substitution, ZWJ and ZWNJ under manual joiners, ligatures of 16 components with marks, CGJ without GDEF, lookups going on after a ligature's last component, variation selectors after joiners, CGJ between marks that compose, fallback marks over composite glyphs and single-point contours. All match HarfBuzz.
- **Unit tests** with hand-built fonts, 43 in all, for every lookup type and format, lookup flags, FeatureVariations, extension lookups, marks on ligature components, the legacy `kern` table and fallback positioning, fixtures whose expected output comes from HarfBuzz (19 cases), and font fallback.
- **Robustness.**
  - The test fonts truncated at every length, and copies with random bytes changed, shape without a panic.
  - Hostile lookups stop within the budget: a context that calls itself and grows the buffer, 200 subtables whose long backtracks match and whose lookaheads fail, ligatures that renumber a long run of marks, nested edits that move a run of marks back and forth. Long runs shape in linear time.
  - Offsets placed two bytes short of 2³² fail instead of overflowing; the tests run on `i686-pc-windows-msvc` too.
- **Independent review.** Codex reviewed the engine in several rounds.
  - The first found 17 issues: work outside the budget (digests, planning, GSUB edits, context records, cursive chains), offsets and positions that could overflow, quadratic deletion of default ignorables, and differences from HarfBuzz in clusters, ligature components, `rvrn` stages, ZWJ in mark features, Hangul and cross-stream kerning.
  - The next compared synthetic fonts with HarfBuzz and found differences in alternates shared by features, Hangul masks and marks on nested ligatures, which led to the mask model above. One of these rounds was cut short by the service's content filter.
  - The next to last found 8: two 32-bit overflows, CGJ classed as a mark without GDEF, lookups resuming inside a ligature, three loops outside the budget, and two doc comments.
  - A review of those fixes found 4: scans in `kern` and fallback positioning still outside the budget, and two test comments that said more than their tests check.
  - Codex's review on the pull request found 4 more: graphemes with a variation selector after a joiner kept from normalization, `zh-Hans-TW` tagged as Traditional, fallback mark positions from the outline's box rather than the header's, and glyphs moved by nested edits outside the budget. Its second pass found 3: fallback passing over a font that covers a cluster through composition, and CGJ decided after recomposition, both fixed; the third, that GPOS should not pass over a blocking CGJ, does not hold for HarfBuzz 10.4.0, which passes hidden characters in GPOS and places the text as this engine does.

  They are fixed and tested, apart from what is listed above as not supported.

## Measurements

Windows 11, i5-11400H, `cargo run --release -p duydas-text --example shape_bench`, ranges over five runs. Chat messages of 41–90 characters in Turkish, Japanese and English, shaped as one run:

| Font | Per character | One-character run |
|---|---|---|
| Segoe UI (TrueType) | 233–548 ns | 1.2–2.2 µs |
| Yu Gothic Medium (TrueType, collection) | 220–508 ns | 1.2–2.3 µs |
| Minion Pro (CFF) | 202–442 ns | 1.1–1.7 µs |

A mixed message of 284 characters over the three fonts splits into 14 runs in 16–27 µs, and itemizing and shaping it takes 87–140 µs (306–492 ns per character). From these numbers, a screen of 50 messages of 100 characters would take about 2.5 ms to shape the first time; that is an estimate, not a measurement. Shaped runs are meant to be cached with the layout.

## Consequences

- **Next in step 4:**
  - paragraph layout: line breaking (ADR 0025) over shaped runs, and bidirectional text;
  - a glyph cache keyed by font, glyph, size and subpixel offset;
  - the font list to bundle: a Latin font with Turkish letters ahead of Noto Sans JP.
- **Arabic, Hebrew and the Indic scripts** need bidirectional layout and script-specific shapers. They are not in Duydaş's first languages; until then such text shows with the default features, left to right.
- **Keeping up with HarfBuzz.** The comparison scripts are not in the repository: they need HarfBuzz and fontTools. When HarfBuzz changes behaviour, the dump test (`dump_shaping_for_comparison`) and the fixture writer (`write_fixtures_for_comparison`) give the data to compare again.
